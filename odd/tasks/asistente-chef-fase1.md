# Asistente "Chef" — Phase 1 (backend, text-only)

## Specs

Scope: phases 2 (voice in/out), 3 (UI) and 4 (superadmin UI polish) are OUT of this document.

- **S1 — Closed tool set.** The model can only call these tools; anything else is rejected by the backend and never executed.
  - Write (require confirmation, see S5): `agregar_items(mesa, items[{producto, cantidad, nota?}])`, `cancelar_item`, `liberar_mesa`.
  - Read (no confirmation): `consultar_mesa(mesa)`, `consultar_menu(producto)`, `mesas_libres()`, `ventas_hoy()` (only with analytics permission).
  - The model never produces SQL and never receives a `tenant_id`; `tenantId` and `userId` come only from `req.tenant.id` / `req.user.id`.
- **S2 — Mesa resolution is done by the backend.** The model returns the raw text ("mesa cuatro", "la de la terraza", "domicilio"). The backend normalizes (lowercase, strip accents, number words → digits) and matches against `mesas.numero` and `mesas.descripcion` (current schema: `numero` max 10 chars, `descripcion` max 100 chars; virtual tables `tipo='virtual'` from migration 037 cover "domicilio"). No new column in Phase 1 (ASSUMPTION: `descripcion` is enough as alias; revisit if testing shows otherwise). 0 or >1 matches → the assistant asks, it never guesses.
- **S3 — Product resolution is done by the backend.** Same normalization against `productos.nombre`, scoped by `tenant_id`, only available (`disponible`) and active products. Ambiguous/no match → ask the user. Price always comes from the DB (never from the model or the client), reusing `AgregarItemService`.
- **S4 — Reuse existing services for every write.** Writes go through `AbrirPedidoService`, `AgregarItemService`, `LiberarMesaService` (and the existing item-cancel path), so validations, stock check, SSE (`RealtimeEvents`) and tenant ownership (`TenantOwnership`) stay identical to the manual flow. No parallel re-implementation of that logic.
- **S5 — Confirmation before any write.** The first call returns a human-readable proposal ("Agregar 4 ramen a la terraza 2. ¿Confirmo?") plus a one-time `confirmation_id`. The write executes only on a second call with that id. The pending action is bound to `tenantId + userId`, expires (TTL), is single-use, and is re-validated at execution time. ASSUMPTION: in-memory `CacheService` is acceptable (single-process app, same limit as SSE).
- **S6 — Access control, three layers.** (1) Tenant has the `asistente` add-on (new row in `addons`, migration 128). (2) The individual user has the `asistente.usar` permission, added to `utils/permisosCatalogo.js` (NOT by migration), granted by the superadmin as a per-user exception, default roles = none. (3) Each tool re-checks the permission the equivalent manual action needs (`mesas.*`, `pos.vender`, analytics, ...). The assistant never grants a user more than they have.
- **S7 — Prompt-injection posture.** Product names, client names and order notes (writable by anonymous QR customers) are untrusted. They are sent to the model only as data inside tool results, never concatenated into the system prompt; the system prompt states that tool-result text is data. Tools exposed are minimal and none can modify configuration, users, prices or payments.
- **S8 — Data minimization.** Nothing about clients (phone, email, document) is sent to the provider. Only table identifiers/aliases, product names, quantities and prices are sent.
- **S9 — Provider abstraction.** A thin `LlmProvider` interface with one `GroqProvider` implementation (tool-calling). Key in `GROQ_API_KEY` (server env only, optional in `config/env.js`: the feature is disabled with a clear error if absent). Model name configurable by env; free-tier limits must be verified against Groq's current docs before launch (they change).
- **S10 — Rate limiting and cost control.** Per-user and per-tenant limits on `POST /api/asistente/comando` (reuse `express-rate-limit` as in `routes/qr_api.js`), plus a request timeout and a max tool-call iterations cap per command. Failure of the provider returns a 503-style message, never a half-executed write.
- **S11 — Audit.** Every command logs to `tenant_audit` via `TenantAuditService.log` (`accion` prefixed `asistente.`): original text, tool name, confirmed or not, result/error. No API key or provider payload in logs.
- **S12 — Idempotency.** Confirmed writes honor the existing `Idempotency-Key` middleware; a repeated `confirmation_id` is rejected.
- **S13 — Per-tenant assistant name.** Stored per tenant (small config table or column, migration 128) and injected in the system prompt. Editing UI is Phase 4; Phase 1 only stores/reads it, default "Chef".
- **S14 — Scope limit.** Questions unrelated to the restaurant get a fixed refusal. The real barrier is S1 (no tools for anything else), the prompt is only secondary.

User-stated examples to keep as acceptance cases (verbatim, Spanish): "salió una orden de un burrito de la casa para la mesa 4", "4 ramen para la mesa 8 o para la mesa de domicilio".
